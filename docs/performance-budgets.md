# Performance budgets

MILESTONES.md §4 decision 44: the budgets are **measured**, not asserted, on a
synthetic five-year, twenty-asset ledger, and optimisation happens only where a
budget fails. This file is the record of that measurement.

> **Status: two budgets met, one blocked.** Every screen read is inside 500 ms
> except the two that value the portfolio in the kernel, and the snapshot job
> runs at 3.3 days/s against a budget of 50. All three have the same cause and
> the same proposed fix, which is a kernel change outside what Milestone 4
> Phase 6 may decide alone — see [The blocked budget](#the-blocked-budget).

## How to re-run

```
supabase start -x logflare,studio,vector      # the stack the numbers are measured against
FF_BUDGETS=1 pnpm test:db                     # the whole tier, including the budgets
FF_BUDGETS=1 pnpm exec vitest run --config vitest.db.config.mts lib/jobs/performance.dbtest.ts
```

`FF_BUDGETS` is why CI does not pay for this: seeding ~20k rows and building
1,256 snapshot days takes about seven minutes. Without the variable the suite
is skipped — the one documented exception to "the database tier never skips",
because the skip means "not asked for", not "no stack".

The ledger is generated by `lib/testing/synthetic.ts` from a fixed seed
(`20260924`), so a surprising number is reproducible exactly. It is seeded
through `seedGoldenPortfolio`, the same helper the golden portfolio uses, so
the figures are measured over the rows a real ledger has.

### D-23: the CSV reader needs no rewrite

20,000 rows parse in **10.4 ms**. D-23 reserved the right to rewrite
`parseCsv` with index scanning if the number failed; it passes by a factor of
48, so the character-by-character reader stays as written. The decision is
closed.

### Fixed here: `coverTotals`

First measurement: **2,855 ms**, the worst read in the table. It asked the
kernel for `quantityAt` once per (snapshot date × asset) — 1,256 × 20 FIFO
walks of each asset's whole history.

An asset's quantity can only change on a date it traded, so the walk now runs
once per traded date per asset and every snapshot date in between reads the
answer off that timeline by binary search: **275 ms**, a 10× improvement, with
no change to what it returns (the model's own tests, which pass dates out of
order, are unchanged and green). Fixed under P6-U1 step 4 — "fix in the
smallest place" — because it is a view model, not the kernel.

## The blocked budget

The three failures above are one cause.

### What it is

`compoundRate` (`lib/calc/series/rate.ts`) walks **every business day from a
lot's open date to the valuation date**, once per lot, multiplying the daily
index factor. The synthetic ledger contributes a monthly lot to each asset for
five years, so the four CDI-linked holdings (`br.cdb`, `br.lci_lca`) carry ~61
lots each, averaging ~625 business days of history:

```
4 assets × 61 lots × ~625 days ≈ 152,000 Decimal iterations — per valuation
```

Measured directly (`valuePortfolio` over subsets of the same ledger):

| Subset                                            | p50 ms |
| ------------------------------------------------- | -----: |
| all 20 assets                                     |    763 |
| only the 7 accrual assets                         |    723 |
| only the 4 CDI-linked (`percent_of_index`) assets |    686 |

**90 % of the cost of valuing this portfolio is four assets' accrual
compounding.** That one loop explains all three failures: `valueLedger` (one
valuation), `readContributionWindow` (two valuations, at both ends of the
window), and the snapshot job (one valuation per day × 1,256 days ≈ 290 ms
each).

### Why it was not fixed here

The fix is a change to the kernel's arithmetic, and P6-U1 authorises "a
date-ranged read, a narrower select, a read view" — the same boundary that
sends an index to the maintainer as a decision. Two further reasons to stop
here rather than push it through unattended:

1. **The golden does not protect it.** `packs/br/fixtures/portfolio.json` has
   exactly one lot per accrual asset, so it never exercises a multi-lot
   regrouping. A change made under a green golden would be a change made under
   a test that cannot see it.
2. **Decimal multiplication is not associative in the last digit.** Any
   regrouping shifts results by ~1e-28 relative — far inside the 1e-8 golden
   tolerance, but it is still a deliberate change to how money is computed,
   which is the one thing Milestone 2 exists to have pinned down.

### The proposal, with numbers

**Chain the lots instead of restarting each one.** Sort an asset's lots by
`openedOn` descending and accumulate:

```
factor(openedOn_i, asOf) = factor(openedOn_i, openedOn_{i+1}) × factor(openedOn_{i+1}, asOf)
```

Identical daily terms, regrouped. Cost per asset falls from Σ Nᵢ to N_max —
about **60× less work** on this ledger (152,000 → ~1,250 iterations).

Projected, from the measured split (~261 ms accrual + ~29 ms everything else
per snapshot day):

|                          |        now |               after the kernel fix |
| ------------------------ | ---------: | ---------------------------------: |
| `valueLedger`            |     815 ms |            ~110 ms (inside budget) |
| `readContributionWindow` |   1,486 ms |            ~250 ms (inside budget) |
| snapshot job             | 3.3 days/s | ~30 days/s (**still short of 50**) |

**The kernel fix alone does not reach 50 days/s.** The remaining ~29 ms per
day is dominated by one `writeDay` round trip per day (`SnapshotStore.writeDay`
is one statement per date by design — "one day's rows in ONE statement: all or
nothing"). Reaching the budget needs that batched across days as well, which
changes the job's atomicity contract.

So there are two decisions for the maintainer, and they are separable:

1. **Chain the accrual lots** (kernel, `lib/calc/valuation/accrual.ts` +
   `lib/calc/series/rate.ts`). Wants a new multi-lot accrual case in the BR
   golden, hand-derived by `derive_expected.py`, before it lands — otherwise
   nothing proves it.
2. **Batch `writeDay` across days** (job, `lib/jobs/snapshots-store.ts`), or
   revise decision 44's 50 days/s to a number an all-or-nothing per-day write
   can reach.

### What it means in practice, today

Not a broken product, but a slow first import: the daily cron values one new
day and is instant. It is the **backfill** that is slow — a newly imported
five-year history takes ~380 s of work against a 60 s cron budget
(`CRON_MAX_DURATION_SECONDS`), so it resumes across roughly seven invocations.
At two crons a day, a five-year backfill completes in about three days, during
which the analysis screens show a partial history. A one-year history
backfills within a single run.

This is worth knowing before the first real import (MILESTONES.md's
production-data gate), which is why it is recorded here rather than left in a
commit message.
